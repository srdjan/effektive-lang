## 1. Authority and goal

This document is the plan authority for the reset. It holds the findings review, the inherited open items and their dispositions, the phases, and the verification of each phase. When another document disagrees with this plan about reset work, this plan wins. `docs/status.md` remains the authority for the project status and the stopping rule.

The goal is a simple and stable base for future work. The reset preserves all current functionality. It changes no language form, no diagnostic code or message, no emitted TypeScript, no IR wire format, no command-line flag, and no language server reply. It closes every open item that older plans carry, so that one live backlog remains.

The reset adds no feature. Each task must remove drift, remove duplication, make a boundary clearer, or make the gate faster or safer. A task that only moves lines without one of these results is not in the plan.

## 3. First principles

The repository must do five things. It must turn Effektive source into checked, typed IR. It must check that IR independently. It must emit Effect-TS from the IR. It must serve the command-line tool, the language server, the VS Code client, and the playground from one core. It must prove each of these with fast tests, slow tests, golden files, and the behavior capture.

These invariants hold through the reset:

1. The layers depend only downward. The core has no Deno call and no import from `src/cli`, `src/host`, or `src/lsp`.
2. The independent validator shares no code with the checker. The checker and the validator duplicate rules on purpose, because the validator is a differential oracle.
3. The typed IR is the contract between the checker and every later stage. `src/core/ir.ts` stays a copy of the sibling `typed-ir.ts`. The IR node name `nominal` is part of IR version 6 and stays.
4. Emitted text is byte-identical. The golden files in `fixtures/golden/` and the mutation fixtures in `fixtures/validate/` do not change, except in RB7 if the user selects it.
5. The three package entry points in `deno.json` keep their exported names. Two exported types can change shape in RB4, under Decision 3 (a) only: the `TypeReader` method names, and the members of `NodeFact`, which `CheckedModule` exposes (`frontend.ts:38`, `docs/api.md:255-258`). No outside code imports the package.
6. The website links to `fixtures/applications/portable-publisher`. That path stays.

## 7. Phases

### Rules for every phase

Work on local `main`. Make one commit for each unit. Run `deno task check` before each commit, and test its exit status, not the exit status of a pipe. Do not run `golden:update` or `validate:update` to make a test pass. RB1 and RB8 change only documents and tests. They do not need a behavior capture.

For each phase that changes `src/`, run the behavior capture against the commit before the phase: `deno task behavior:capture <phase-base> HEAD`. The result must show 0 new and 0 missing records. If the phase also moves or renames tests, hold the test set constant with the procedure in `docs/solutions/workflow-issues/behavior-capture-hold-tests-constant.md`. Up to two extra or missing `program` records with the result `[]` and nothing else are run variance (see the solution note): run another capture to confirm it. Any other difference fails the unit. The capture runs both suites on two revisions, so record its time at first use.

For each phase that changes the emitter, lowering, or checker, also prove byte identity of the generated fixtures:

```sh
deno task golden:update && deno task validate:update && git diff --exit-code fixtures/
```

This command must print nothing and exit 0. If it changes a file, discard the change with `git checkout -- fixtures/` and fix the code.

Phases RB1 to RB7 touch mostly different files. These overlaps fix the order: RB3 and RB4 both edit `check.ts`, and RB3 unit 5 and RB4 unit 1 edit the same lines `check_expr.ts:1036-1064`, so RB3 comes before RB4. RB4 unit 6 and RB5 unit 1 both edit `src/lsp/server.ts`, so RB4 comes before RB5. RB0, RB1, and RB8 all edit `AGENTS.md` and `docs/status.md`, so they run in that order. RB8 comes last. Each phase that adds, removes, or moves a source file updates the source file map in the same commit, because the RB1 test fails otherwise.
