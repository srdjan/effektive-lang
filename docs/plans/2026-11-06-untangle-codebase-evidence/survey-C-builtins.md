# Survey: slice C, builtin families as a cross-cut

Method. I traced three "add one builtin" commits (random/randomInt 2cf3cd2, log 5008fc0, now/Instant 0578a14) and two "remove one family" commits (c9e358a fibers, 92ec013 Schedule). I excluded `src/core/validate/` from every count. Line numbers are from HEAD.

Touch-set, non-validator files, for a new effect leaf builtin (random/randomInt, 2cf3cd2): `check_builtins/effect.ts` (rows + handler), `tables.ts:162` (NodeFact kind), `resolve.ts:61` (PRELUDE name), `lower.ts:234` (IR builder), `ir.ts:224` (Expr kind), `emit/shape.ts:161` (ROWS), `emit/expr.ts:1719` (leaf case list), `emit/families/effect.ts:30,134,150` (kind union, emission), `emit/module_state.ts:49` (EffectModule), `editors/vscode/syntaxes/effektive.tmLanguage.json:130` (name list). That is 10 non-validator files. Removing a whole family (c9e358a fibers, 92ec013 Schedule) touched 24 non-validator `src/core` files, because a handle type is spelled out per layer (see Hidden links, last item).

Registry verdict. `check_builtins/registry.ts` is the single source for the checker rows, and callers do not bypass it. The only outside importer of family row tables is `check_expr.ts:115` (`FAMILY_ROWS`), plus the test. Type-level enforcement is strong: `Rows<N,C>` requires one row per `PreludeName`, `Kebab<K>` forces `fact.kind` to match the row key (`rows.ts:13-31`), `PositionalBuilders` in `lower.ts` and `ShapeTable` in `shape.ts` require one entry per kind. So most links are compiler-checked. The findings below are the links that are still unchecked or repeated.

## Hidden links
- **C.H1** `check_builtins/rows.ts:13-31` + each row, e.g. `check_builtins/ref.ts:62-77`, `effect.ts` rows (`fail`, `random`, `randomInt`, ...): the row key `makeRef` already determines the fact kind `make-ref` (the `Kebab` type proves it), yet every row writes `fact: { kind: "make-ref" }` by hand. The kind is derivable from the key; the compiler only checks the copy.
- **C.H2** `check_builtins/*.ts` prologue arity (`direct(2, ...)`, `piped(3,...)`, `optionalLast(1,...)`) + `lower.ts:213-260` builders (`arg(0)`, `arg(1)`) + `emit/expr.ts:1632-1639` (`counts` table: `all:[1,2], traverse:[2,3], map:[2], filter:[2], fold:[3]`) + `emit/expr.ts:1202,1209` (`args.length !== 2`, `!== 3` for map/filter/fold): arity of one builtin is written in the checker prologue, in the lowering builder indices, and twice in the emitter. Nothing ties them; a changed arity fails only at run time (internal error).
- **C.H3** `check_builtins/collections.ts:40,166,176,213,228` + `tables.ts:211` (`name: "map"|"filter"|"fold"|"all"|"traverse"`) + `emit/expr.ts:393-401` (`effectCollectionBuiltin`) + `emit/expr.ts:1623-1693` (leaf switch on `filter`/`fold`/default) + `emit/expr.ts:1166-1199` (`builtinCall` switch on `map`/`filter`/`fold`) + `ids.ts:48-62` (`builtinInstanceId` / `builtinInstanceName`): the five collection builtin names are written as string unions in four places and are carried to the emitter inside a string identity `value:<module>#$builtin/<name>/<hash>`. The emitter parses the name back out of the string. Which of the five is "leaf" and which is "non-leaf" (the pure vs effect choice) is decided in `emit/expr.ts:1504-1508` by a separate rule. Adding a sixth collection builtin needs all of these, and the default branches (`emit/expr.ts:1192` "no emission form") are runtime-only.
- **C.H4** `ir.ts:202` (inline 15-op literal union for `schema`) + `tables.ts:178-200` (18-op union incl. decode/encode/make) + `check_builtins/schema.ts:74,104-220` (`SCHEMA_BUILTINS` table with `op`) + `schema.ts:260-285` (`SCHEMA_HANDLERS`) + `schema.ts:1325-1347` (16 rows that all repeat `{ prologue: SCHEMA_PROLOGUE, handle: SCHEMA_HANDLE }`) + `resolve.ts:86-101` (16 names) + `emit/families/schema.ts:44-300` (switch) + `lower.ts:777-800`: the Schema op set is spelled in IR, in the fact type, in the SchemaBuiltin table, in the handler table, in the rows, in the resolver and in the emitter. `ir.ts:202` and `tables.ts:178-200` are the same list typed twice by hand (IR minus the three ops lowered to other kinds); no `Exclude<>` links them.
- **C.H5** `check_builtins/schema.ts:323,371,890` (reads option `on` of `schemaDefaultKey`) + `lower.ts:1058-1085` (`schemaArguments` re-filters the record for `"on"`, hard-codes the three `default-*` op names and rebuilds the record type) + `check_builtins/schema.ts:225-229` (`DEFAULT_KEY_OPS`): the `on` option and the op names that depend on it are known to checker and lowering separately. Lowering re-parses a record the checker already analysed.
- **C.H6** `check_builtins/effect.ts:507,561-562` (`LOG_KEYS`, `level`/`fields`) + `lower.ts:826-848` (`invokeLog` finds `fields` by name in the lowered record, with a comment "the checker proved a literal options record"): the option names are repeated, and lowering depends on the checker's proof. Same pattern for repeat/retry options: `effect.ts:128-129` (`OPTION_KEYS`), `effect.ts:711-728` (`times`), `emit/families/effect.ts:167` (prints the text `{ times: ${e.times} }`), while `repeat` passes the whole options record through (`emit/families/effect.ts:177-185`) so its field names are only checked in the checker.
- **C.H7** `emit/expr.ts:1719-1722` (case list of effect leaf kinds) + `emit/families/effect.ts:24-33` (`EffectLeafKind` union) + `emit/families/effect.ts:~125-200` (the switch) + `emit/shape.ts:161-170` (`leaf: "leaf"` flag) + `emit/calls.ts:75-92` (`LEAF_CALLS`) + `emit/calls.ts:44-70` (`OPERAND_CALLS`): one builtin's emission is routed by one of five mechanisms (family switch, `LEAF_CALLS`, `OPERAND_CALLS`, in-class case such as `update-ref`/`ensure`/`catch`, or the `default` of `leaf()`). The compiler proves each kind has one, but a reader cannot tell which without searching. The `leaf` flag in `shape.ts` and the `leaf()`/`structural()` choice in `expr.ts` are two statements of the same fact; a mismatch fails at run time (`emit/expr.ts:1619` `is not a leaf`).
- **C.H8** `resolve.ts:54-110` (`PRELUDE`, 30+ `shadowable: true` entries) + `editors/vscode/syntaxes/effektive.tmLanguage.json:130` (hand-edited name list in a regex) + `ls` of rows: the prelude name list is copied into the TextMate grammar on every builtin commit (2cf3cd2, 5008fc0, 0578a14, e45a929, 92ec013, c9e358a each edit it). `tests/vscode_client_test.ts:148` compares it with `PRELUDE_NAMES`, so drift is caught, but the copy is still edited by hand. ## Root-cause notes
Cause 1: a builtin is described by name in many tables, and each table repeats a part of the same fact (name, arity, kind, op list). The compiler already forces one entry per kind (`Rows`, `PositionalBuilders`, `ShapeTable`, `OPERAND_CALLS`), so the "must add" part is safe. The unchecked part is the repeated facts: arity, option-record field names, op unions, and the collection-name unions. One fix: a per-builtin descriptor `{ name, kind, arity, optionKeys }` in `check_builtins` that `resolve.ts` (name, shadowable), `lower.ts` (arity for `arg(i)`), and the emitter (collection arity) read. Then `PRELUDE`, the kebab fact key, the arity literals and the tmLanguage list come from one place.

Cause 2: collection builtins cross the checker/lowering/emitter boundary as a string inside an identity (`ids.ts:48-62`). The emitter re-derives name, arity and leaf-ness from that string (`emit/expr.ts:393-401`, `1623-1693`, `1166-1199`). Fix: lower these as typed IR kinds (`map`, `filter`, `fold`, `all`, `traverse`), as every other builtin already is; the string parsing, four name unions and the `counts` table then go away. This changes IR, so it is a plan item, not a quick edit; golden output must stay identical.

Cause 3: Schema has an op union copied between `ir.ts:202` and `tables.ts:178-200`, a 16-row table that repeats `SCHEMA_BUILTINS`, and lowering that re-filters the `on` option. Fix: derive IR op type from the fact op type with `Exclude`, derive `SCHEMA_ROWS` from `SCHEMA_BUILTINS`, and let the checker store the selected op and the stripped argument list in the fact so lowering does not re-read the options record. The same idea fixes `log`'s `fields` lookup (`lower.ts:826`).

Cause 4: a handle type (sink, stream, provider, ref, retry-schedule, schema) is cut by layer: types, type_ir, type_lower, type_show, signatures, provenance, emit/types, fields, decls, module_state. Removal commits touch 24 files. Fix: one record per type kind with show/lower/emit hooks, or accept the cost; this is the largest item and cannot be measured as a leverage number without a plan. It is "probable" that most of the 24 are exhaustive-switch edits that the compiler already guides.

Cause 5: the checker side of families is uneven. `Some` and the `"own-arity"` rows bypass `runPrologue`; `refCall` and `collectionCall` re-dispatch on name; registry carries three exports used by one test. Fix: give `Some` a family file with a context method in `BuiltinContext`, and split name ladders into per-name handlers sharing small helpers; then `CoreRowName`, `CORE_ROW_NAMES` and the `CORE_ROWS` ordering comment disappear.

Not read (budget): `check_builtins/stream.ts`, `scope.ts`, `layer.ts` bodies, and `emit/families/stream.ts`, `scope.ts`, `layer.ts` beyond kind unions. Claims about them rest on grep counts, not full reads.
